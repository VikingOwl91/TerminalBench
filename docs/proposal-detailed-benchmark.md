# TerminalBench 詳細化提案 v2 — 計測品質・VTワークロード・忠実度検証の拡張

## 1. 背景

[proposal-terminal-bench.md](proposal-terminal-bench.md) の推奨案(案C)は既に実装済みで、6シナリオ・8メトリクス(`shell.startup`, `cmd.overhead`, `render.throughput`[`plain`/`ansi`/`cjk`], `scroll.proxy`, `input.latency`[`idle`/`loaded`], `resource.mem`/`resource.cpu`[`idle`/`load`])を `bin/tbench run`、比較・回帰検知を `bin/tbench compare`(Markdown/HTML、`--threshold`)として運用できている(`README.md`, `lib/`)。

実運用でこの計測系そのものの信頼性に関わる4つの課題が判明した。

1. **同時実行の干渉**: 2つのターミナルで同時にフルスイートを走らせたところ、Ghostty の `render.throughput` が 70→13 MB/s まで汚染された。他の `tbench` プロセスを検出する仕組みも、逐次実行を促すガイドも存在しない。
2. **`resource.cpu[idle]` の汚染**: 直前シナリオ(フラッド負荷)の残留効果が macOS `ps` の減衰平均 `%cpu` に残り、`idle` が真に idle でない(p95 243% を観測)。シナリオ間の settle(冷却待ち)が無い。
3. **フレームスキップ疑惑**: Terminal.app で `ansi` > `plain` という不自然な結果が出た。`cat` のスループットは「PTY への書き込み消費速度」であり、実際に画面へ描画されたことを保証しない(README にも既に明記済みの限界だが、検出手段が無い)。
4. `zsh-timer` バックエンド(hyperfine 不在時のフォールバック、または `render.throughput`/`scroll.proxy` のように常に `sink_terminal=1` でこの経路を通るシナリオ)にウォームアップフェーズと外れ値除去が無い(`lib/stats.sh` `tbench_measure_zsh`)。

本提案は、これら4つの課題への対処(A)を土台に、VT(仮想端末)ワークロードの詳細化(B)、描画忠実度の検証(C)、真の入力レイテンシ測定(D)、複数エミュレータの自動オーケストレーション(E)、比較の統計的厳密化(F)までを整理し、実装コストと限界を明示した上で推奨実施順を示す。

## 2. 施策一覧

以下 A〜F の6施策を、目的・手法概要・実装コスト(S/M/L)・精度と限界・依存の5項目で整理する。実装コストの目安は S=数時間〜半日、M=1〜3日、L=1週間以上(新規の権限取得フローや外部ツールの検証を含む)とする。

| 施策 | 一言で言うと | 実装コスト | 追加依存 |
|---|---|---|---|
| A. 計測品質の強化 | 既存メトリクスの汚染源(settle不足・同時実行・warmup不足)を潰す | S〜M | なし |
| B. VTワークロードの詳細化 | vim/less/top相当のカーソル移動・部分再描画パターンを追加計測 | M | なし |
| C. 描画忠実度検証 | フレームスキップを検出、または「検出できない」ことを申告する | S(probe)/L(キャプチャ) | なし(probe)/画面収録権限(キャプチャ) |
| D. 真のkeypress→photon入力レイテンシ | GUIオートメーションで物理キー相当のレイテンシを測る | L | アクセシビリティ+画面収録権限、pyobjc等 |
| E. オーケストレーション | 複数エミュレータの逐次自動実行で同時実行事故を構造的に防ぐ | M | なし(macOS限定) |
| F. 統計の強化 | bootstrap信頼区間・有意差判定で「本当に変化したか」を判定する | S(前提)+M | なし(SciPy不使用の自前実装) |

### A. 計測品質の強化(最優先)

**目的**: 「同じ環境で測っているはずなのに数値が汚染される」問題を潰し、既存8メトリクスの数値そのものの信頼性を上げる。新しい計測種別は増やさない。

**手法概要**:
- **シナリオ間 settle**: 各シナリオ実行後に固定時間(既定 0.5〜1s、`--settle` で調整可)スリープし、直前の負荷(CPU/GPU/端末バッファ)を鎮める。特に `resource_footprint` の `idle` サンプリング直前と、`render_throughput`/`scroll_proxy` の各バリアント間に挿入する。
- **他 tbench プロセス検出**: 実行開始時に `pgrep -f 'bin/tbench'`(自プロセス除外)でロックファイル(`results/.tbench.lock`、PID + タイムスタンプ記録)を確認し、既存プロセスがあれば警告して確認プロンプトを出す(`--force` でスキップ可)。README にも「フルスイート実行中は他のターミナルで tbench を動かさない」ガイドを追記。
- **`zsh-timer` の warmup/外れ値除去**: `tbench_measure_zsh` に固定 warmup 回数(既定3、hyperfine の `--warmup 3` に合わせる)を追加し、本計測の前に破棄する。外れ値除去は IQR(四分位範囲)ベースの簡易フィルタ(1.5×IQR 外を除外)を `tbench_median`/`tbench_p95` 計算前に挟む形で実装する。
- **環境メタデータの記録**: `lib/report.sh` の `meta` に `power_source`(`pmset -g batt` 由来)、`display_refresh_hz`(`system_profiler SPDisplaysDataType` 由来、取得コスト高なので `--full-meta` オプトイン)、`gpu`(同コマンド)、`low_power_mode`(`pmset -g` の `lowpowermode`)を追加。macOS 専用、取得失敗時は該当フィールドを省略(既存の "resource.* はmacOS専用" 方針と一貫)。
- **adaptive runs**: `--runs` の代わりに `--adaptive`(例: 信頼区間の半幅が中央値の5%未満に収束するまで、上限50回まで追加試行)を追加実装。既存の固定 `--runs` はそのまま維持し、オプトインの別モードとする。

**実装コスト**: S(settle・ロックファイル・warmup/外れ値除去・環境メタデータ) / M(adaptive runs — 収束判定ロジックと上限制御が必要)

**精度・限界**: settle は「マシンが落ち着くのを待つ」ヒューリスティックであり、根本的な同時実行不可制約(A自体)を解決するものではない。ロックファイル方式は `tbench` 経由の同時実行しか検出できず、他アプリの負荷(ビルド中の Xcode 等)は検出対象外。IQR 外れ値除去はサンプル数が少ない(`--runs` が小さい)場合に誤って正常値を弾くリスクがある。

**依存**: 追加なし(`pmset`/`system_profiler` は macOS 標準コマンド、権限昇格不要)。

**CLI 例**:

```sh
# settle 秒数と adaptive runs を指定
bin/tbench run --settle 1.0 --adaptive --output results/latest.json

# 他 tbench プロセスが動いている場合は警告して確認を求める
# (--force で確認をスキップして強制実行)
bin/tbench run --force
```

### B. VT ワークロードの詳細化(vtebench 系)

**目的**: 現状の `render.throughput` は「大量テキストの `cat` 流し込み」1パターンのみで、実際のエディタ/ページャ操作(vim/less のようなカーソル移動・部分再描画中心のワークロード)の描画性能を代表していない。vtebench が測るような、より粒度の細かい VT シーケンス処理性能を追加する。

**手法概要**: 新シナリオ種別 `kind: vt_workload` を追加し、以下のサブシナリオを YAML で定義する。
- **カーソル移動**: `\e[H`(ホーム)や `\e[<n>;<m>H` を大量発行し、カーソルジャンプのコスト単体を計測。
- **部分書き換え**: 固定画面上の一部の行だけを繰り返し書き換える(top/htop 相当のパターン)。
- **alt-screen 全画面再描画**: `\e[?1049h` で alt-screen に入り、vim/less 相当の全画面書き換えを繰り返す。
- **scrolling region**: `\e[<top>;<bottom>r` でスクロール領域を限定し、その範囲内でのスクロール速度を計測(全画面スクロールとの差分が出るはず)。
- **SGR 属性大量変更**: 1文字ごとに前景色/背景色/太字等を切り替える(色つきログの過酷なケース)エスケープシーケンス列を流し込む。
- 各シナリオは事前生成した固定エスケープシーケンス列ファイルを `cat` で流し込み、計測手法自体は既存の `tbench_collect_ms_samples`(`sink_terminal=1`)を再利用する。
- 加えて、**DECSET 2026(synchronized output)対応照会**: 対象端末が `\e[?2026$p` に応答するか(DECRQM)を起動時に1回照会し、`meta.synchronized_output_supported` として記録する(C. の忠実度検証の前提情報としても使う)。

**実装コスト**: M(シーケンス生成スクリプト5本 + 新 `kind` ディスパッチ追加。既存の `tbench_run_scenario_render_throughput` のパターンを流用できるため、ゼロからの新規実装ではない)

**精度・限界**: あくまで `cat` 経由のスループット測定であり、実際のアプリ(vim等)の入力待ち・レンダリングループとは異なる負荷特性になる(近似ワークロード)。SGR 属性変更頻度やカーソル移動パターンは恣意的に選んだ固定パターンであり、「代表的な実アプリのログ」を統計的にサンプリングしたものではない。

**依存**: 追加なし。シーケンス生成は `printf`/`awk` 等の標準コマンドで完結。

**CLI 例**:

```sh
# VT ワークロードのシナリオ群だけを実行
bin/tbench run --scenario vt-cursor-move
bin/tbench run --scenario vt-partial-redraw
bin/tbench run --scenario vt-altscreen-redraw
bin/tbench run --scenario vt-scroll-region
bin/tbench run --scenario vt-sgr-heavy
```

**新規メトリクス案**:

| メトリクス | 単位 | 説明 |
|---|---|---|
| `vt.cursor_move` | ms | 固定回数のカーソルジャンプが完了するまでの時間 |
| `vt.partial_redraw` | ms | 固定範囲の部分書き換えループが完了するまでの時間 |
| `vt.altscreen_redraw` | ms | alt-screen 全画面再描画ループの完了時間 |
| `vt.scroll_region` | ms | スクロール領域限定時のスクロール完了時間 |
| `vt.sgr_heavy` | ms | SGR属性大量変更を伴う出力の完了時間 |

### C. 描画忠実度(フレームスキップ検出)

**目的**: 課題3(Terminal.app で `ansi` > `plain` という逆転)の根本原因を確かめる。`cat` の完了時間は「PTY 消費速度」であり、GPU 合成側がフレームをスキップ/バッチ処理していれば「速く終わった」ように見えても実際は描画が追いついていない可能性がある。この2つを区別する検出手段を用意する。

**手法概要(2案を比較)**:

| 手法 | 概要 | 実装コスト | 精度・限界 | 依存 |
|---|---|---|---|---|
| **マーカー行+画面キャプチャ方式** | 出力の各N行ごとに一意なマーカー文字列(行番号埋め込み)を挿入。`cat` 完了直後に画面キャプチャ(macOS: `screencapture -x`、より高頻度なら `ScreenCaptureKit` 経由の連続キャプチャ)を取り、OCR またはピクセルパターンマッチで最終フレームにどのマーカーが実際に描画されているかを検証する | L | `screencapture` 単発なら実装は軽いが「最終フレームの内容確認」しかできず、途中のフレームスキップ有無は分からない。連続キャプチャ+OCRは精度は高いが実装・処理コストが大きく、OCR誤読リスクもある | `screencapture`(標準、権限: 初回に画面収録許可が必要)。連続キャプチャ+解析は Swift/Python 実装が別途必要になり、"追加依存なし" の既存方針から逸脱する |
| **DECSET 2026 (synchronized output) probe 方式** | 対象端末が synchronized output に対応していれば、`\e[?2026h`(開始)〜`\e[?2026l`(終了)で囲んで出力すると、端末側が「一括で確定フレームとして描画」することが保証される。この対応可否(B. で取得済みの `meta.synchronized_output_supported`)を元に、非対応端末では「フレームスキップの可能性あり」という注記をレポートに自動付与するに留める | S | 実際にフレームスキップを検出するのではなく、「検出できない/リスクがある」ことを申告するだけの間接的な手法。対応端末でも synchronized output を使わない通常計測(現状の `render.throughput` 等)にはそのままでは効果がない | 追加なし。DECRQM 照会は標準エスケープシーケンスで完結 |

**推奨**: DECSET 2026 probe 方式を先に実装し(S、依存なし)、レポート上で「この端末はフレームスキップを検出できない/対応している」を明示する。マーカー行+画面キャプチャ方式は精度は高いが実装コストと権限要求(画面収録許可)が大きく、優先度を下げて将来検討とする。

**依存**: probe 方式は追加なし。画面キャプチャ方式は `screencapture`(macOS標準、要:システム設定で画面収録許可)。

**レポートへの反映例**(probe方式、`meta` に追加するフィールド):

```json
{
  "meta": {
    "synchronized_output_supported": false,
    "frame_skip_risk_note": "This terminal does not respond to DECRQM ?2026; render.throughput/scroll.proxy numbers may not reflect a fully-rendered final frame."
  }
}
```

### D. 真の入力レイテンシ(keypress → photon)

**目的**: 現状の `input.latency` は PTY ラウンドトリップ(`zpty` 経由でバイトを書いて読み戻すまで)であり、README にも明記の通り「真のキー入力〜画面反映(photon)レイテンシではない」。実際のキー押下からピクセルが変化するまでを測る設計案を示す。

**手法概要**: macOS の `CGEvent` API でキーイベントを注入し(`CGEventCreateKeyboardEvent` + `CGEventPost`)、注入直後から対象ウィンドウの特定領域(例: プロンプト直後の1文字分のピクセル)を高頻度(60〜120Hz相当)でポーリングし、色/輝度変化を検出した時刻との差分を latency とする。ポーリングは `CGWindowListCreateImage` または `ScreenCaptureKit` のフレームストリームで実装する。

**実装コスト**: L(GUIオートメーション+画面ポーリングのネイティブ実装が必要。既存の zsh/シェルスクリプトの枠組みでは完結せず、Swift または Python(pyobjc)での補助バイナリ/スクリプトが要る)

**精度・限界**: `CGEvent` 注入によるキー入力は、物理キーボードの実キー押下と完全に同一の経路を通るとは限らない(一部アプリはハードウェアイベントとソフトウェア注入イベントを区別する)。ポーリング頻度がディスプレイのリフレッシュレート(B.で取得する `display_refresh_hz`)を下回ると photon タイミングの解像度が粗くなる。ウィンドウが最前面かつ他プロセスの妨害がない状態を保証する必要があり、自動化そのものの信頼性(フォーカス制御の失敗等)がノイズ源になる。既存手法(`typometer` 等)との比較では、`typometer` は物理カメラで真の光学的遅延を測るためこの CGEvent+ポーリング方式より精度が高いが、専用ハードウェア(高速カメラ)が必要で自動化・CI 組み込みには向かない。本方式はソフトウェアのみで完結する分、typometer より低精度だが再現性・自動化容易性で勝る。

**依存**: `CGEvent`/`ScreenCaptureKit` は macOS 標準フレームワークだが、**アクセシビリティ権限(キー入力注入)** と **画面収録権限(ポーリング)** の両方が必要 — sudo は不要だが、初回実行時にユーザーの明示的な権限付与(システム設定)が必須。Python 実装の場合は `pyobjc` の追加インストールが必要になる(現行の "追加依存なし" 方針からの明確な逸脱、要合意)。

### E. オーケストレーション(`tbench orchestrate`)

**目的**: 課題1(同時実行の干渉)を根本解決する。複数エミュレータでの比較は現状「ユーザーが手動で各エミュレータを開いて順に `tbench run` する」運用(README「Comparing reports across terminal emulators」)であり、うっかり同時実行してしまう事故が起きやすい。これを自動的に**逐次**実行するコマンドに置き換える。

**手法概要**: `bin/tbench orchestrate --terminals ghostty,iterm2,terminal-app`(設定は `.app` バンドルIDまたは既知のショートカット名にマッピングするテーブルを `lib/` に持つ)を新設。各エミュレータについて:
1. `open -a <App> <起動スクリプト>` で新規ウィンドウを起動し、その中で `bin/tbench run` を実行させる(起動スクリプトは一時シェルスクリプトを生成し、完了後に結果 JSON パスをマーカーファイルに書いて終了する)。
2. A. のロックファイル機構を使い、次のエミュレータの起動は前段の完了(マーカーファイル出現)を待ってから行う — これにより複数ターミナル同時実行を構造的に防止する。
3. 全エミュレータの実行完了後、生成された JSON を自動的に `bin/tbench compare` に渡してレポートを生成する。

**実装コスト**: M(`open -a` によるアプリ起動+完了待ちポーリングのオーケストレーションロジック。既存の `run`/`compare` はそのまま再利用できるため、新規の計測ロジックは不要)

**精度・限界**: `open -a` で新規ウィンドウ/タブが確実に「フォーカスされた対話的ターミナル」になる保証はエミュレータ実装依存(一部はウィンドウを裏で開くだけでフォーカスしないことがあり、`render.throughput` 等の tty 依存計測に影響しうる)。全エミュレータを1台のマシン上で**逐次**実行するため、A.の同時実行問題は解決するが、実行時間は合計で線形に伸びる(3エミュレータなら約3倍)。

**依存**: 追加なし(`open` は macOS 標準)。Linux では `open -a` 相当のエミュレータ起動コマンドがまちまちなため、この機能は当面 macOS 限定とする。

**CLI 例**:

```sh
# ghostty → iterm2 → Terminal.app の順に自動実行し、最後に比較レポートを生成
bin/tbench orchestrate --terminals ghostty,iterm2,terminal-app \
  --output-dir results/orchestrate-$(date +%Y%m%d) \
  --compare-format html
```

### F. 統計の強化(bootstrap 信頼区間・有意差判定)

**目的**: 現状の `bin/tbench compare --threshold` は「中央値の変化率が閾値を超えたか」という単純な比較のみで、その差がノイズによるものか統計的に意味のある変化かを区別できない。

**手法概要**: `lib/compare.py` に以下を追加する。
- **Bootstrap 信頼区間**: 各メトリクスの生サンプル(現状JSONは median/p95/stddevのみを保持しており生サンプルを含まないため、まず `bin/tbench run` 側で `--keep-samples` オプションを追加し生の ms サンプル配列をJSONに含める必要がある)からリサンプリング(既定1000回)し、中央値の95%信頼区間を算出する。
- **有意差判定(Mann-Whitney U検定)**: baseline/latest 2群の生サンプルに対しノンパラメトリック検定を適用し、p値を算出。正規性を仮定しないため、ベンチマークのようなスキューした分布(hyperfine出力等)に適する。
- `--threshold` モードに `--significance`(既定 p<0.05)を追加し、「変化率が閾値を超え、かつ統計的に有意」な場合のみ回帰として扱うオプションを提供(既存の閾値のみ判定モードもデフォルトのまま残す・後方互換)。

**実装コスト**: M(`compare.py` は Python なので `random`/標準ライブラリのみで bootstrap は実装可能。Mann-Whitney U 検定は SciPy 依存にするか、標準ライブラリのみで簡易実装するかの選択が要る — SciPy 依存は現行の "python3標準のみ" 方針からの逸脱になるため、簡易自前実装(順位和計算)を推奨) / **前提**として `run` 側の `--keep-samples` 追加が先に必要(S)

**精度・限界**: 生サンプルをJSONに残すため出力ファイルサイズが増える(`--keep-samples` はオプトインとし既定はオフで現状互換を維持)。Bootstrap信頼区間は元のサンプル数(既定20)が少ないと区間が広くなり、実用上は `--runs`/`--adaptive`(A.)を大きくしないと恩恵が薄い。Mann-Whitney U検定はサンプル数が極端に少ない(<5程度)と検定力が不足し、有意差なしと出やすい。

**依存**: 追加なし(SciPy を使わない自前実装を選ぶ前提)。`--keep-samples` は `run` 側の変更が前提条件。

**CLI 例**:

```sh
# 生サンプルを含めて計測
bin/tbench run --keep-samples --output results/baseline.json

# 変化率10%超 かつ p<0.05 の場合のみ回帰として扱う
bin/tbench compare results/baseline.json results/latest.json \
  --threshold 10% --significance 0.05
```

## 3. 既存機能との互換性

- A〜Fのいずれも既存の JSON スキーマ・`--runs`・`--scenario`・`--shells` オプションの後方互換を壊さない。新規フィールド(`meta.power_source` 等)・新規オプション(`--settle`, `--adaptive`, `--keep-samples`, `--significance`)はすべてオプトインまたは既定値付きの追加とする。
- `--keep-samples`(F.の前提)によるJSON肥大化以外は、既定の出力サイズ・実行時間への影響は軽微(A.のsettleによる実行時間増加が唯一の例外で、フルスイートで数秒〜十数秒程度の増加が見込まれる)。
- E.のオーケストレーションは `run`/`compare` の上位に位置するラッパーであり、両者のロジックを変更しない。

## 4. リスクと前提

- D.(真の入力レイテンシ)とC.の画面キャプチャ方式は、現行の「追加依存なし・sudo不要」という設計原則から明確に逸脱する(アクセシビリティ権限・画面収録権限・pyobjc等の追加インストールを要する)。着手前にこの方針転換自体の合意が必要。
- A.のロックファイル方式は `tbench` 経由の同時実行のみを検出対象とし、他アプリ由来の負荷(ビルド中の Xcode、バックグラウンドの Time Machine 等)は検出できない。数値の完全なクリーン計測を保証するものではなく、あくまで「最も起きやすい事故(tbenchの多重起動)」への対処である点を利用者に周知する必要がある。
- E.のオーケストレーションはmacOS限定機能であり、Linux/CI環境では従来通りの手動逐次実行運用が必要になる。

## 5. 推奨実施順

| フェーズ | 施策 | 理由 |
|---|---|---|
| **フェーズ1** | A(計測品質の強化) | 最優先。既存8メトリクスの数値そのものが汚染されている状態では、B以降で新しい計測を増やしても信頼できない。実装コストもS〜Mで着手しやすい |
| **フェーズ2** | E(オーケストレーション) | Aのロックファイル機構をそのまま活用でき、課題1(同時実行干渉)を構造的に解決する。手動運用のヒューマンエラーを排除する効果が大きい |
| **フェーズ3** | C(DECSET 2026 probe のみ)+ F(bootstrap/有意差判定、`--keep-samples`込み) | どちらも既存基盤への追加で完結し、依存追加なし。Cはprobe方式のみを先行実装(画面キャプチャ方式は見送り)。Fは`compare`の判断精度を底上げする |
| **フェーズ4** | B(VTワークロードの詳細化) | 新シナリオ種別の追加だが既存パターンの流用で実装できる。忠実度検証(C)と統計強化(F)が整った後に、より詳細なワークロードを測る土台が整う |
| **フェーズ5(将来検討・要合意)** | D(真の入力レイテンシ)+ C(画面キャプチャ方式) | どちらも実装コストL、GUIオートメーション権限や追加依存(pyobjc等)を要し、現行の「追加依存なし」方針からの逸脱を伴う。着手する場合は方針変更の合意を先に取る |

フェーズ1〜3は既存の依存ゼロ方針を維持したまま着手可能。フェーズ4は許容範囲の実装コストで既存基盤の延長線上にある。フェーズ5は明確なスコープ拡大(GUI自動化・追加依存)を伴うため、着手前に個別のGo/No-Go判断を推奨する。
